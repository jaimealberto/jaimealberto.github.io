Cloudflare Workers como webhook receptor: HMAC, Gotify y cero puertos

JaimeAlberto
21-06-2026
Desarrollo, Sysadmin

Sun Tzu no esperaba al enemigo en campo abierto. Elegía el terreno y obligaba al adversario a acudir a él.

Un sysadmin no debería abrir puertos para que los servicios externos entren. Debería elegir dónde se recibe la llamada.

GitHub quiere avisarte cuando alguien hace un push. Stripe quiere avisarte cuando llega un pago. Cualquier servicio externo quiere enviarte un webhook.

El problema: para recibirlo necesitas una URL pública. Y una URL pública normalmente significa un puerto abierto en tu router, una IP fija o un servidor en la nube.

El Worker actúa como ese punto de recepción elegido: vive en el edge de Cloudflare, verifica que quien llama es quien dice ser mediante firma HMAC, y solo entonces pasa el mensaje al interior de la red — sin que el router abra nada.

El problema de los webhooks en el homelab

Un webhook es una petición HTTP POST que un servicio externo envía a tu endpoint cuando ocurre algo: un push en GitHub, un pago en Stripe, una alerta en Grafana. La URL a la que apunta tiene que ser accesible desde internet.

En un homelab detrás de un router doméstico, eso significa una de estas opciones:

  • Abrir un puerto en el router y apuntar a un servidor interno — expones IP y puerto
  • Usar un VPS intermediario — infraestructura extra que mantener
  • Usar ngrok o similar — dependencia de terceros, URL aleatoria en el plan gratuito

O usar un Worker de Cloudflare como endpoint público. Sin puertos abiertos. Sin VPS. La URL es tuya (webhook.tudominio.com) y el código de validación también.

La arquitectura: Worker + Tunnel

El flujo completo:

  1. GitHub envía el webhook a webhook.tudominio.com/github
  2. Cloudflare lo intercepta y ejecuta el Worker en el edge
  3. El Worker valida la firma HMAC del payload — si no es válida, 401
  4. El Worker reenvía el mensaje a Gotify via Cloudflare Tunnel
  5. Gotify notifica al móvil — sin que el router haya abierto un solo puerto

La clave es el paso 4: el Worker puede llamar a URLs externas, y si tu Gotify está expuesto con Cloudflare Tunnel, tiene una URL HTTPS pública. El tráfico va de Cloudflare a Cloudflare, sin salir a internet abierto.

Validación HMAC: verificar que GitHub es GitHub

Sin validación de firma, cualquiera que conozca tu URL puede enviarte webhooks falsos. GitHub firma cada petición con HMAC-SHA256 usando un secreto compartido que tú defines al configurar el webhook.

El proceso:

  1. GitHub concatena el payload con el secreto y calcula SHA-256
  2. Incluye el resultado en la cabecera X-Hub-Signature-256: sha256=<hex>
  3. Tu Worker repite el cálculo con el mismo secreto y compara

Si coinciden, la petición es auténtica. Si no, alguien está intentando inyectar datos falsos.

La Web Crypto API de Workers permite hacer este cálculo sin dependencias externas:

async function verifyHMAC(body, signature, secret) {
  const encoder = new TextEncoder()
  const key = await crypto.subtle.importKey(
    'raw',
    encoder.encode(secret),
    { name: 'HMAC', hash: 'SHA-256' },
    false,
    ['sign']
  )
  const mac = await crypto.subtle.sign('HMAC', key, encoder.encode(body))
  const hex = Array.from(new Uint8Array(mac))
    .map(b => b.toString(16).padStart(2, '0'))
    .join('')
  return `sha256=${hex}` === signature
}

La comparación directa con === es suficiente aquí porque el Worker no tiene estado entre peticiones y no es vulnerable a timing attacks de la misma forma que un servidor persistente. Si quieres ser estricto, puedes usar crypto.subtle.timingSafeEqual cuando esté disponible en el runtime.

El código completo del Worker

addEventListener('fetch', event => {
  event.respondWith(handleRequest(event.request))
})

async function handleRequest(request) {
  if (request.method !== 'POST') {
    return new Response('Method Not Allowed', { status: 405 })
  }

  // Leer el body antes de cualquier otro procesamiento
  const body = await request.text()
  const signature = request.headers.get('X-Hub-Signature-256')
  const eventType = request.headers.get('X-GitHub-Event')

  if (!signature || !await verifyHMAC(body, signature, WEBHOOK_SECRET)) {
    return new Response('Unauthorized', { status: 401 })
  }

  // Ignorar eventos que no nos interesan
  if (eventType !== 'push') {
    return new Response('OK', { status: 200 })
  }

  const payload = JSON.parse(body)
  const repo    = payload.repository?.full_name ?? 'desconocido'
  const author  = payload.pusher?.name          ?? 'desconocido'
  const message = payload.commits?.[0]?.message ?? 'sin mensaje'

  await fetch(`${GOTIFY_URL}/message`, {
    method: 'POST',
    headers: {
      'X-Gotify-Key':  GOTIFY_TOKEN,
      'Content-Type':  'application/json',
    },
    body: JSON.stringify({
      title:    `Push en ${repo}`,
      message:  `${author}: ${message}`,
      priority: 5,
    }),
  })

  return new Response('OK', { status: 200 })
}

async function verifyHMAC(body, signature, secret) {
  const encoder = new TextEncoder()
  const key = await crypto.subtle.importKey(
    'raw',
    encoder.encode(secret),
    { name: 'HMAC', hash: 'SHA-256' },
    false,
    ['sign']
  )
  const mac = await crypto.subtle.sign('HMAC', key, encoder.encode(body))
  const hex = Array.from(new Uint8Array(mac))
    .map(b => b.toString(16).padStart(2, '0'))
    .join('')
  return `sha256=${hex}` === signature
}

WEBHOOK_SECRET, GOTIFY_TOKEN y GOTIFY_URL son variables de entorno que el Worker recibe en tiempo de ejecución — no están en el código.

Secrets: credenciales sin hardcodear

Los secrets se gestionan vía API y nunca aparecen en el script:

source ~/.config/cloudflare/api_tokens.env

# Añadir el secreto del webhook de GitHub
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/workers/scripts/webhook-receptor/secrets" \
  -H "X-Auth-Email: $CF_EMAIL" \
  -H "X-Auth-Key: $CF_GLOBAL_KEY" \
  -H "Content-Type: application/json" \
  --data '{"name":"WEBHOOK_SECRET","text":"tu-secreto-aqui","type":"secret_text"}'

# Token de Gotify
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/workers/scripts/webhook-receptor/secrets" \
  -H "X-Auth-Email: $CF_EMAIL" \
  -H "X-Auth-Key: $CF_GLOBAL_KEY" \
  -H "Content-Type: application/json" \
  --data '{"name":"GOTIFY_TOKEN","text":"tu-token-gotify","type":"secret_text"}'

# URL de Gotify (puede ser un plain_text si no es sensible)
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/workers/scripts/webhook-receptor/secrets" \
  -H "X-Auth-Email: $CF_EMAIL" \
  -H "X-Auth-Key: $CF_GLOBAL_KEY" \
  -H "Content-Type: application/json" \
  --data '{"name":"GOTIFY_URL","text":"https://gotify.tudominio.com","type":"secret_text"}'

Los secrets se almacenan cifrados en la infraestructura de Cloudflare y nunca son legibles tras escribirlos, ni desde la API ni desde el dashboard.

Despliegue y pruebas con curl

El despliegue sigue el mismo patrón que en el artículo anterior sobre Workers: multipart con metadata.json y el script:

# metadata.json — sin bindings KV esta vez, solo el script
cat > metadata.json << 'EOF'
{
  "body_part": "script",
  "compatibility_date": "2024-01-01"
}
EOF

curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/workers/scripts/webhook-receptor" \
  -H "X-Auth-Email: $CF_EMAIL" \
  -H "X-Auth-Key: $CF_GLOBAL_KEY" \
  -F "metadata=@metadata.json;type=application/json" \
  -F "script=@worker.js;type=application/javascript"

Luego un DNS CNAME (o AAAA a 100::) para webhook.tudominio.com y una ruta de zona:

curl -X POST \
  "https://api.cloudflare.com/client/v4/zones/$CF_ZONE_ID/workers/routes" \
  -H "X-Auth-Email: $CF_EMAIL" \
  -H "X-Auth-Key: $CF_GLOBAL_KEY" \
  -H "Content-Type: application/json" \
  --data '{"pattern":"webhook.tudominio.com/*","script":"webhook-receptor"}'

Para probar sin tocar GitHub, simula el webhook con curl. El secreto compartido para este ejemplo es test-secret:

BODY='{"repository":{"full_name":"jaime/mi-repo"},"pusher":{"name":"jaime"},"commits":[{"message":"fix: corregir bug en el dashboard"}]}'

# Calcular la firma HMAC-SHA256
SIG="sha256=$(echo -n "$BODY" | openssl dgst -sha256 -hmac "test-secret" | awk '{print $2}')"

curl -X POST https://webhook.tudominio.com/github \
  -H "Content-Type: application/json" \
  -H "X-GitHub-Event: push" \
  -H "X-Hub-Signature-256: $SIG" \
  --data "$BODY"
# → OK

Si la firma no coincide:

curl -X POST https://webhook.tudominio.com/github \
  -H "Content-Type: application/json" \
  -H "X-GitHub-Event: push" \
  -H "X-Hub-Signature-256: sha256=firmainvalida" \
  --data "$BODY"
# → Unauthorized

Para conectar GitHub: en el repositorio, Settings → Webhooks → Add webhook. URL: https://webhook.tudominio.com/github. Secret: el mismo que pusiste en WEBHOOK_SECRET. Content type: application/json.

El Worker como receptor no es solo un patrón elegante — es la única forma de recibir tráfico externo en una red privada sin ceder control del perímetro. No hay puerto abierto que cerrar, no hay IP que rotar, no hay superficie que reducir. El perímetro es Cloudflare, y el control es tuyo.

Si quieres llevar este modelo más lejos — autenticación, micro-segmentación y acceso sin VPN — el artículo sobre Zero Trust en el homelab cubre exactamente eso.
