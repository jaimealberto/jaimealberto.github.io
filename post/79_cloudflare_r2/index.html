Cloudflare R2: alternativa a S3 sin egress y 10 GB gratis

JaimeAlberto
23-06-2026
Sysadmin, Homelab

El que elige el terreno elige el resultado. Sun Tzu lo escribió pensando en batallas. Los proveedores de nube lo aplicaron a su modelo de precios.

Almacenar en S3 es barato. Mover datos fuera de S3 — hacia internet, hacia otros servicios, hacia tus propios servidores — es donde Amazon recupera el margen.

Se llama egress cost. Cada gigabyte que sale tiene un precio. Pones los datos dentro gratis. Sacarlos te cuesta.

Cloudflare R2 nació para cambiar ese terreno. Sin egress. Sin asteriscos. Con compatibilidad total con la API de S3 — rclone, boto3 y aws-cli funcionan sin cambiar una línea.

Y tiene un caso de uso que nadie documenta bien y que uso constantemente en el homelab: compartir un fichero desde la terminal y obtener una URL pública en dos segundos.

R2 vs S3: el coste que no ves

En almacenamiento en la nube hay dos precios que importan: lo que pagas por guardar datos y lo que pagas por sacarlos.

AWS S3 cobra ambas cosas. El almacenamiento es barato — unos 0,023 $/GB/mes. El egress — transferir datos desde S3 hacia internet — puede llegar a 0,09 $/GB. Si tienes un bucket que sirve contenido, pagas más por el egress que por el almacenamiento.

R2 cobra por almacenar (0,015 $/GB/mes) y por operaciones (PUT, GET), pero el egress es cero. Los datos pueden salir libremente hacia internet, hacia Workers o hacia cualquier destino sin coste adicional.

Cloudflare R2 Amazon S3
Almacenamiento 0,015 $/GB/mes 0,023 $/GB/mes
Egress a internet 0 $/GB Hasta 0,09 $/GB
Class A (PUT, DELETE) 4,50 $ / millón 0,005 $ / 1.000
Class B (GET, HEAD) 0,36 $ / millón 0,0004 $ / 1.000

Para uso personal y homelab, los precios de pago son irrelevantes — el plan gratuito cubre con creces el uso real.

Plan gratuito de R2

R2 incluye una capa gratuita generosa. Cloudflare pide una tarjeta de crédito para verificar la cuenta antes de activar R2, pero no hay cargo mientras no superes los límites.

Recurso Límite gratuito
Almacenamiento 10 GB
Class A (PUT, DELETE, LIST) 1.000.000 / mes
Class B (GET, HEAD) 10.000.000 / mes
Egress Sin límite, sin coste

Para compartir ficheros desde el homelab, 10 GB son más que suficientes si limpias los objetos con cierta regularidad. Para backups permanentes de datos críticos, el plan de pago sigue siendo competitivo dado el egress cero.

Crear bucket y API token

Bucket

Desde el dashboard de Cloudflare (R2 → Create bucket), o via API:

source ~/.config/cloudflare/r2.env  # CF_ACCOUNT_ID, CF_API_TOKEN

curl -s -X POST \
  "https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/r2/buckets" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"name": "mi-bucket"}' | jq '.result.name'

El nombre del bucket debe ser único dentro de tu cuenta. Si vas a exponer objetos públicamente, elige un nombre que no revele la estructura interna de tus sistemas.

API Token

El token para R2 se genera desde el propio dashboard de R2, no desde el panel general de Cloudflare. Ve a R2 → Manage R2 API Tokens → Create API Token.

Para el script de compartir ficheros necesitas:

  • Permissions: Object Read & Write
  • Bucket: el bucket concreto (no “All buckets”)
  • TTL: sin caducidad, o una fecha futura larga

El token genera dos valores: Access Key ID y Secret Access Key. Son las credenciales equivalentes a S3. Guárdalos con permisos 600:

cat > ~/.config/cloudflare/r2.env << 'EOF'
CF_ACCOUNT_ID=tu_account_id
R2_ACCESS_KEY_ID=tu_access_key
R2_SECRET_ACCESS_KEY=tu_secret_key
R2_BUCKET=mi-bucket
R2_PUBLIC_BASE_URL=https://files.tudominio.com
EOF
chmod 600 ~/.config/cloudflare/r2.env

El R2_PUBLIC_BASE_URL lo configuramos en la siguiente sección.

Hacer el bucket accesible públicamente

Para que los ficheros subidos tengan una URL pública hay dos opciones:

1. Subdominio r2.dev (sin configuración adicional)

Dashboard: R2 → tu bucket → Settings → Public Access → Allow Access. Cloudflare asigna una URL pub-xxxx.r2.dev. Funciona sin tocar el DNS, pero el subdominio no es tuyo y no es elegante.

2. Dominio propio (recomendado)

La opción limpia: R2 → tu bucket → Settings → Custom Domains → Connect Domain. El dominio tiene que estar en Cloudflare — si aún usas otro proveedor DNS, en DDNS gratuito con Cloudflare explico cómo moverlo.

files.jaimealberto.io → mi-bucket

Una vez configurado, los objetos quedan accesibles en:

https://files.jaimealberto.io/nombre-del-fichero.ext

El dominio actúa como CDN automático — los objetos se cachean en los edge nodes de Cloudflare sin configuración adicional.

Si en lugar de acceso público necesitas restringir quién puede descargar, Cloudflare Tunnel es el camino: expones el bucket internamente y pones autenticación delante sin abrir ningún puerto.

r2share: subir y compartir desde la terminal

El caso de uso concreto: tienes un fichero, quieres una URL. Sin abrir el navegador, sin arrastrar y soltar, sin WeTransfer.

La API de R2 es compatible con S3, así que aws-cli funciona directamente apuntando al endpoint de R2. Primero, configurar las credenciales:

aws configure set aws_access_key_id "$R2_ACCESS_KEY_ID"
aws configure set aws_secret_access_key "$R2_SECRET_ACCESS_KEY"
aws configure set default.region auto

El endpoint de R2 es https://<account_id>.r2.cloudflarestorage.com. La región siempre es auto — Cloudflare gestiona la ubicación física internamente.

El script:

#!/bin/bash
# r2share — sube un fichero a R2 y devuelve su URL pública
# Uso: r2share fichero.tar.gz
# Uso: r2share fichero.tar.gz nombre-publico.tar.gz

set -euo pipefail
source ~/.config/cloudflare/r2.env

FILE="$1"
REMOTE_NAME="${2:-$(basename "$FILE")}"

if [[ ! -f "$FILE" ]]; then
  echo "Error: fichero no encontrado: $FILE" >&2
  exit 1
fi

aws s3 cp "$FILE" "s3://$R2_BUCKET/$REMOTE_NAME" \
  --endpoint-url "https://$CF_ACCOUNT_ID.r2.cloudflarestorage.com" \
  --no-progress

echo "${R2_PUBLIC_BASE_URL}/${REMOTE_NAME}"

Instalarlo:

cp r2share ~/.local/bin/r2share
chmod +x ~/.local/bin/r2share

En uso real:

r2share config-backup-2026-07-29.tar.gz
# https://files.jaimealberto.io/config-backup-2026-07-29.tar.gz

r2share logs-junio.tar.gz logs-junio-compartido.tar.gz
# https://files.jaimealberto.io/logs-junio-compartido.tar.gz

El segundo argumento es opcional — sirve para dar un nombre limpio al fichero público sin renombrar el original. Útil cuando el nombre local tiene rutas, timestamps internos o información que no quieres exponer en la URL.

Para borrar un objeto cuando ya no lo necesitas:

aws s3 rm "s3://$R2_BUCKET/config-backup-2026-07-29.tar.gz" \
  --endpoint-url "https://$CF_ACCOUNT_ID.r2.cloudflarestorage.com"

Compatibilidad S3: rclone y boto3

La API de R2 es S3-compatible: cualquier herramienta que funcione con S3 funciona con R2 sin cambiar el código. Solo cambia el endpoint.

rclone

rclone es la opción más habitual para backups hacia almacenamiento de objetos. Configurar un remote de R2:

# ~/.config/rclone/rclone.conf
[r2]
type = s3
provider = Cloudflare
access_key_id = tu_access_key
secret_access_key = tu_secret_key
endpoint = https://tu_account_id.r2.cloudflarestorage.com
acl = private

# Backup de directorio
rclone sync ~/importante r2:mi-bucket/importante --progress

# Listar objetos
rclone ls r2:mi-bucket

boto3 (Python)

import boto3

r2 = boto3.client(
    's3',
    endpoint_url='https://tu_account_id.r2.cloudflarestorage.com',
    aws_access_key_id='tu_access_key',
    aws_secret_access_key='tu_secret_key',
    region_name='auto'
)

# Subir
r2.upload_file('fichero.txt', 'mi-bucket', 'ruta/fichero.txt')

# Listar
for obj in r2.list_objects_v2(Bucket='mi-bucket')['Contents']:
    print(obj['Key'], obj['Size'])

La compatibilidad cubre las operaciones habituales — PUT, GET, DELETE, LIST, multipart upload. Las funciones específicas de AWS sin equivalente en R2 (Glacier, S3 Replication, S3 Inventory) no aplican.

Worker opcional: enlaces con expiración

R2 no tiene URLs prefirmadas con expiración automática como S3 (presigned URLs con TTL). Para añadir expiración a los enlaces compartidos, la solución es un Worker de Cloudflare.

El Worker actúa como intermediario: recibe la petición, verifica si el objeto ha superado el tiempo de vida que fijaste al subir, y decide si sirve el fichero o devuelve un 410 Gone. El patrón es el mismo que en Workers como webhook receptor: Worker como capa de control antes de que la petición llegue al recurso.

Para el 90% de los casos del homelab, la expiración manual — borrar el objeto cuando ya no lo necesitas — es suficiente. La solución con Worker tiene sentido si compartes ficheros con personas externas y necesitas garantizar que los enlaces dejan de funcionar pasadas 24 o 48 horas sin tener que acordarte de borrarlos.
